# AutoQueue 项目代码审查报告（大白话版）

> 项目：`@alintever/dsh-plugin-autoqueue`
> 仓库：<https://github.com/alin-ever/dsh-plugin-autoqueue>
> 审查代码版本：`7b21fb6`
> 审查日期：2026-08-29

## 先说结论

这个项目的想法很好：把任务丢进队列，AI 自己执行，做完以后给结果。

但是当前版本还不适合直接拿来跑重要任务，更不适合长时间无人看管。原因不是代码写得难看，而是几个最关键的地方还不够可靠：

- 有的任务可能碰到不该碰的文件；
- 不同任务之间没有真正隔开；
- 点了“停止”，任务也可能继续在后台运行；
- 定时任务可能重复执行，也可能失败一次后永远不再执行；
- 程序崩溃或账本出错时，任务可能丢失；
- 已经归档、界面里看不见的任务，仍可能偷偷执行；
- “无人值守，不要问人”的规则可能根本没有生效；
- 设置页面目前打不开。

一句话概括：**功能框架已经有了，但安全带、刹车和故障恢复还没做好。可以继续开发和测试，不建议马上投入真实使用。**

## 最需要先解决的 10 个问题

### 1. 任务名可以把文件写到不该写的位置

**发生了什么**

系统会拿任务名直接拼成文件路径，但没有检查任务名里是不是带了 `../` 或 `..\\`。

例如有人把任务名写成：

```text
..\..\victim
```

程序就可能跑出自己的任务目录，去覆盖或删除外面的 `victim.md`。

**会造成什么**

- 其他项目的 Markdown 文件可能被覆盖；
- 停止或删除任务时，也可能删到不该删的文件；
- 如果本机接口能被其他网页访问，风险会更大。

**怎么改**

- 任务名只允许中文、英文、数字、短横线和下划线；
- 不允许 `/`、`\\`、`..` 等路径内容；
- 写文件前再次确认最终路径仍在任务目录里面；
- 接口要限制请求大小、请求方式，并确认登录权限。

### 2. 所有 AI 任务住在同一个“房间”里

**发生了什么**

系统本来有能力给每个任务单独建一个工作目录，但默认配置却把整个队列目录共享给所有任务。

这个共享目录里不只有当前任务，还放着：

- 队列总账；
- 其他待执行任务；
- 其他任务的执行结果；
- 所有运行记录。

**会造成什么**

一个 AI 任务可能看到、修改甚至删除其他任务的数据。任务内容如果带有恶意指令，还可能直接改队列总账。

**怎么改**

- 每个任务默认只能访问自己的运行目录；
- 队列总账和收件箱不能放在 AI 默认可写的目录里；
- 只有用户明确选择时，才允许多个任务共享工作区。

### 3. “停止任务”可能只是在界面上停了

**发生了什么**

启动任务需要一点时间。在这个过程中，如果用户马上点“停止”，系统可能先把状态写成“已停止”，但后台会话随后又启动成功。

这时界面显示任务已经停止，实际 AI 仍在继续工作。更麻烦的是，系统以后也不会再检查这个会话。

另外，调用真正的停止接口失败时，当前代码也可能把它当成成功。

**会造成什么**

- 用户以为任务停了，实际还在消耗模型额度；
- AI 可能继续修改文件或调用外部服务；
- 后台留下没人管理的会话。

**怎么改**

- 启动完成后再次检查任务是不是已经被停止；
- 如果已经停止，立刻关闭刚创建的会话；
- 只有后台明确返回“停止成功”，界面才能显示已停止；
- 每次启动都要带唯一编号，避免旧启动结果覆盖新状态。

### 4. 定时任务可能在一分钟内连跑多次

**发生了什么**

程序只判断“现在是否符合 cron 时间”，却没有记录“这一分钟已经执行过了”。

例如每天 08:00 执行的任务，如果很快做完，08:00 这一分钟内下一次扫描仍会认为时间符合，于是再次执行。

**会造成什么**

- 同一份日报发好几次；
- 同一个外部操作重复执行；
- 重复写文件、重复通知、重复扣模型费用。

**怎么改**

为每个计划时间生成一个唯一编号，并记录已经执行过。一个计划时间只能领取一次。

### 5. 定时任务失败一次，后面可能永远不跑了

**发生了什么**

定时任务启动后，原任务文件会被删除。只有任务正常完成时，程序才把下一次需要的文件重新放回去。

如果本次执行失败、卡死或重试次数耗尽，定时计划可能也跟着消失。

**会造成什么**

一个“每天执行”的任务，今天失败一次，明天、后天都不会再执行，而且没有明显提示。

**怎么改**

把“每天几点执行”与“今天这一次执行”分开保存。今天失败只能结束今天这一次，不能删除整个定时计划。

### 6. 程序崩溃时，任务可能永久丢失

**发生了什么**

任务启动成功以后，代码先删除收件箱里的任务文件，然后才把后台会话编号保存到账本里。

如果程序刚好在这两步之间崩溃：

- 收件箱文件已经没了；
- 账本又不知道后台会话是谁；
- 重启后任务虽然显示“待执行”，但再也没有东西能把它启动起来。

账本文件如果格式错误或版本不一致，当前代码还会直接当成“空账本”，下一次保存时可能覆盖掉原来的数据。

**怎么改**

- 先把后台会话完整保存到账本，再删除收件箱文件；
- 账本读坏时必须停下来报警，不能假装里面没有任务；
- 保存损坏账本的备份，并为旧版本提供升级步骤。

### 7. 归档只是“藏起来”，不一定真的停用

**发生了什么**

一个还没到执行时间的任务可以被归档。归档后它从界面消失，但对应的任务文件和定时计划还在。

扫描程序又没有检查“这个任务是不是已经归档”，所以到时间后仍可能执行。

**会造成什么**

- 用户以为任务已经收起来，不会再跑；
- 实际任务在看不见的地方继续运行；
- 出问题时很难发现和停止。

**怎么改**

- 归档或停用的任务必须禁止被扫描器启动；
- “归档”“暂停计划”“停止本次执行”要做成三个含义明确的按钮；
- 界面要提供“查看归档任务”和“恢复”入口。

### 8. “无人值守规则”可能根本没有安装成功

**发生了什么**

项目会修改 Agent 配置，告诉 AI：不要等待人回答、遇到问题自己换方案、做完写报告。

但当前代码用正则表达式修改 YAML，匹配规则写错了，常见的 YAML 写法根本匹配不到。禁用“向用户提问”工具的判断也不准确。

**会造成什么**

看起来是无人值守任务，实际 AI 可能中途问一句“接下来怎么办”，然后一直等在那里。

**怎么改**

- 用正式的 YAML 解析工具修改配置，不要用字符串和正则硬改；
- 启动时检查规则内容是否真的存在；
- 增加自动测试，确认提问工具确实被禁用。

### 9. 设置页面现在打不开，修完后还可能改错配置

**发生了什么**

设置页面引用了两个不存在的变量，所以用户一打开设置就会报错。

即使把这个报错修掉，页面也没有读取完整的真实配置，而是用一批默认值填空。用户只想改一个选项，点保存时可能顺手把其他真实配置都改成默认值。

另外，页面上修改任务目录后，后台实际上仍可能继续使用旧目录。

**会造成什么**

- 设置页面不可用；
- 一次普通保存可能偷偷改掉多个配置；
- 页面显示的新目录与程序实际使用的目录不一致。

**怎么改**

- 打开页面时读取完整配置；
- 只提交用户真正改过的字段；
- 前端和后端共用同一份配置说明和默认值；
- 如果运行中不支持换目录，就不要在页面上提供这个选项。

### 10. 一个任务卡死，可能拖住整个队列

**发生了什么**

系统按顺序一个一个检查正在运行的任务。如果排在前面的任务一直没有返回，后面的任务就得不到检查。

这些后台请求还没有超时限制。一个请求永远不结束时，整个轮询器可能一直卡着。

**会造成什么**

- 后面的任务做完了也不能结算；
- 超时和截止时间失效；
- 重试过程中还可能留下新的孤儿会话。

**怎么改**

- 每个后台请求都设置超时；
- 一个任务报错不能影响其他任务；
- 可以少量并行检查，但要限制同时执行数量；
- 首次启动和重试使用同一套清理规则。

## 还有哪些次要问题

下面这些问题没有前面 10 个紧急，但也需要处理：

- 系统提供的“版本号”不会随大部分任务变化而更新；
- 请求失败后，重复提交同一个请求编号可能被误认为已经成功处理；
- webhook 里可能同时出现“状态是运行中、结果却是已完成”；
- 手动停止任务不会发送 webhook；
- 所谓指数退避实际上可能每次都只等待相同时间；
- 重试后，旧执行记录仍可能显示“正在运行”；
- 任务列表和实时推送每 10 秒重复发送完整正文，大任务多时很浪费内存和网络；
- AI 工具请求没有超时，可能一直等；
- AI 工具成功提示可能显示任务名 `undefined`；
- 打开的任务详情不会自动更新；
- `*/30 * * * *` 等定时规则会显示成看不懂的文字；
- 非法时间可能不报错，反而立刻执行任务。

## 项目做得比较好的地方

这份审查不是说项目没有价值。当前代码里已经有一些不错的基础：

- host、执行器、账本、文件处理和前端大体上做了模块拆分；
- 已经考虑任务重试、并发限制、未读状态、报告和 webhook；
- 写账本时尝试使用临时文件再替换，方向是对的；
- README、API 文档和设计文档比较齐全；
- 看板和 AI 工具已经具备基本产品形态。

问题主要出在“极端情况下会不会出错”和“出错以后能不能恢复”。这类问题可以修，但需要先把规则定清楚，不能只继续增加 `if` 和 `catch`。

## 建议怎么安排修复

### 第一阶段：先把安全带和刹车装好

1. 限制任务名，堵住目录逃逸；
2. 每个任务使用独立工作目录；
3. 修复停止与启动同时发生的问题；
4. 后台停止失败时必须如实报错；
5. 给本机接口增加请求限制和权限检查。

完成这些以前，不要运行会修改真实文件、调用真实业务系统或产生较高模型费用的任务。

### 第二阶段：保证任务不重复、不丢失

1. 一个 cron 时间点只能执行一次；
2. 单次失败不能删除整个定时计划；
3. 调整收件箱删除与账本保存顺序；
4. 账本损坏时停止写入并保留备份；
5. 归档任务绝不能继续执行。

### 第三阶段：恢复无人值守和设置功能

1. 正确修改并检查 Agent 配置；
2. 修复设置页面；
3. 读取完整配置，只保存用户改动；
4. 修复归档列表和恢复入口；
5. 修正 webhook、任务详情和定时文案。

### 第四阶段：提高长期运行稳定性

1. 所有后台请求增加超时；
2. 每个任务独立处理错误；
3. 实时推送改成摘要或只推变化；
4. 统一重试、清理和执行记录；
5. 增加自动化测试和发布前检查。

## 修完以后怎么验收

- [ ] 带 `../` 或 `..\\` 的任务名会被拒绝；
- [ ] 同时创建两个任务，它们看不到彼此的工作目录；
- [ ] 在任务启动过程中马上点停止，后台不会留下活会话；
- [ ] 每分钟执行的任务，一分钟内只执行一次；
- [ ] 定时任务今天失败，下一次计划时间仍会执行；
- [ ] 在保存任务的每一步模拟崩溃，重启后任务不会丢；
- [ ] 账本内容损坏时，程序报警并保留原文件；
- [ ] 归档的定时任务到点后不会执行；
- [ ] AI 在无人值守模式下不会停下来等用户回答；
- [ ] 打开设置页面不会报错；
- [ ] 只修改一个配置时，其他配置保持不变；
- [ ] 一个后台请求卡住时，其他任务仍能正常结算；
- [ ] webhook 的状态和结果一致；
- [ ] 大量任务和慢客户端不会让内存持续上涨。
